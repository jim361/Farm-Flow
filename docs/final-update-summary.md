## 2. 전체 변화 요약

기존 코드는 프론트 화면과 일부 백엔드 기능이 분리되어 있었고, 실제 센서 데이터 흐름이나 사용자별 온실 구분, 배포 환경까지 하나의 시연 흐름으로 연결되어 있지는 않았다.

최종 코드는 회원가입부터 온실 UID 발급, 장치 등록, MQTT 센서 시뮬레이터, 실시간 대시보드, 로직빌더, 템플릿, 스케줄러, 알림, Cloudflare 도메인 배포까지 하나의 시연 가능한 시스템으로 연결되도록 수정되었다.

| 구분 | 업데이트 전 | 업데이트 후 |
| --- | --- | --- |
| 사용자 구분 | 계정과 센서 데이터 분리가 불명확 | 회원가입 시 온실 UID를 발급하고 UID 기준으로 센서/장치/데이터 분리 |
| 센서 연동 | 실제 MQTT 시연 흐름 부족 | MQTT 브로커와 웹 센서 시뮬레이터를 통해 온도, 습도, CO2, 조도, 제어기 상태 시연 가능 |
| 대시보드 | 정적/제한적 표시 중심 | MQTT 기반 센서 값 변화와 알림/제어 상태 반영 |
| 장치 등록 | 로직빌더와 시뮬레이터 연계 부족 | 등록된 센서/제어기를 로직빌더에서 활용 가능하도록 개선 |
| 로직빌더 | 기본 노드와 조건 설정이 시연 요구와 불일치 | 센서, 조건, 제어기 구조를 유지하면서 조건값과 제어 동작 설정 가능 |
| 템플릿 | 일부 템플릿 비어 있음, 편집/저장 흐름 불명확 | 기본 템플릿을 채우고 편집/저장/삭제 흐름 개선 |
| 스케줄러 | 시간 반영과 기간 표시가 부족 | 시작일~종료일 기반 일정과 타임라인 반영 개선 |
| 배포 | 로컬 실행 중심 | Cloudflare Tunnel과 도메인 `farmflow.iotbigdata.store`로 외부 접속 가능 |
| 장애 대응 | 부팅 직후 네트워크 지연 시 터널 실패 가능 | Cloudflare DNS/API 대기 및 터널 재시도 로직 추가 |

## 3. 백엔드 변경 사항

### 3.1 인증 및 사용자 관리

- 회원가입, 로그인, 사용자 조회 흐름을 백엔드 중심으로 정리했다.
- JWT 인증 구조를 추가하여 로그인 후 API 요청을 인증된 사용자 기준으로 처리한다.
- 사용자 엔티티에 `greenhouseUid`를 추가하여 계정마다 독립적인 온실 식별자를 갖도록 했다.
- 회원가입 시 랜덤 온실 UID가 생성되도록 하여 여러 사용자가 같은 시스템에 접속해도 데이터가 섞이지 않게 했다.
- 아이디 찾기 흐름은 이메일 로그인 구조와 충돌하지 않도록 등록한 이름 기반 탐색 방향으로 조정했다.

### 3.2 장치 및 온실 UID 기반 데이터 분리

- 장치 엔티티와 DTO에 온실 UID, 장치 UID, 장치 타입 정보를 반영했다.
- 장치 등록 시 센서와 제어기를 구분하고, 등록된 장치를 로직빌더에서 사용할 수 있도록 API와 프론트 데이터 흐름을 맞췄다.
- 기존처럼 고정된 `GH-001`만 사용하는 방식이 아니라 사용자별 `greenhouseUid`를 기준으로 센서/장치 데이터가 연결되도록 개선했다.

### 3.3 MQTT 연동

- MQTT 설정과 파이프라인을 추가했다.
- 기존 단일 토픽 중심 구조에서 아래와 같은 시연용 토픽 구조를 처리할 수 있게 했다.
  - `farm/sensor/#`
  - `farmflow/devices/+/telemetry`
  - `farmflow/greenhouses/+/devices/+/telemetry`
- MQTT telemetry 메시지를 받아 센서 값을 해석하고, 온실 UID와 장치 UID 기준으로 상태를 갱신한다.
- 룰 엔진이 제어 명령을 MQTT command topic으로 발행할 수 있도록 했다.
- Mosquitto 설정을 추가하고 Docker Compose에 MQTT 브로커를 포함했다.

### 3.4 룰 엔진 및 제어 로직

- 온도, 습도, CO2, 조도 센서 조건을 처리하는 규칙 구조를 추가했다.
- 로직빌더에서 설정한 조건이 만족되면 연결된 제어기 명령이 실행되도록 룰 엔진을 확장했다.
- 단순히 "조건 만족 시 ON"만 하는 것이 아니라, 조건 해제 시 OFF 명령도 처리할 수 있도록 개선했다.
- 제어기 상태 변화가 대시보드와 알림 흐름에 반영되도록 연결했다.

### 3.5 워크플로우와 템플릿

- 워크플로우 저장, 수정, 삭제, 배포 상태 관리를 보강했다.
- 템플릿 적용 시 flowData를 복사해 실제 워크플로우로 사용할 수 있도록 개선했다.
- 기본 템플릿 데이터가 비어 있던 문제를 보완하고, 시연에 맞는 센서-조건-제어기 흐름을 포함했다.
- 편집 후 새 이름 저장만 가능한 흐름이 아니라 기존 템플릿/워크플로우 관리 흐름을 명확히 했다.

### 3.6 대시보드 API

- 대시보드에서 센서 지표와 장치 상태를 가져올 수 있는 API 구조를 추가했다.
- 프론트 대시보드가 백엔드와 MQTT 상태를 기반으로 표시될 수 있도록 연결점을 마련했다.

## 4. 프론트엔드 변경 사항

### 4.1 로그인 및 사용자 흐름

- 로그인/회원가입 API 호출을 실제 백엔드와 맞췄다.
- 로그인 후 사용자 정보와 온실 UID를 프론트 상태에 저장하고, API 요청에서 활용하도록 했다.
- 아이디 찾기, 비밀번호 찾기, 프로필 수정 UI를 현재 인증 구조에 맞게 조정했다.

### 4.2 대시보드

- 센서 값 카드와 날씨/상태 영역의 디자인을 정리했다.
- MQTT 시뮬레이터에서 센서 값이 바뀌면 대시보드 모니터링 값이 변하는 흐름을 구현했다.
- 알림센터가 항상 사이드바처럼 노출되던 문제를 개선하고, 알림이 있을 때 확인/해제 가능한 형태로 수정했다.
- 룰 엔진에 의해 제어기가 켜지거나 꺼질 때 사용자가 상태 변화를 볼 수 있도록 했다.

### 4.3 장치 등록

- 시뮬레이터에 있는 센서/제어기 이름과 장치 등록 화면의 입력 흐름을 맞췄다.
- 센서와 제어기를 등록한 뒤 로직빌더에서 해당 장치를 활용할 수 있도록 데이터 흐름을 정리했다.
- 스프링클러, 보광등 같은 제어기도 UID를 직접 입력할 수 있게 하여 센서 시뮬레이터와 동일한 방식으로 연결되도록 했다.

### 4.4 로직빌더

- 로직빌더 구조를 센서, 조건, 제어기 블록으로 다시 정리했다.
- 사용자가 센서 블록을 끌어오고 조건 블록에서 직접 기준값을 입력할 수 있도록 했다.
  - 온도: 몇 도 이상/이하
  - 습도: 몇 퍼센트 이상/이하
  - CO2: 몇 ppm 이상/이하
  - 조도: 몇 lux 이상/이하
- 제어기 블록에서는 ON/OFF 동작을 설정할 수 있도록 했다.
- 단순한 "빠른 설정"이 아니라 사용자가 직접 조건과 제어 흐름을 구성하는 방식으로 수정했다.

### 4.5 템플릿

- 워크플로우 템플릿 화면의 카테고리 UI를 전체 디자인 톤에 맞게 정리했다.
- 기본 템플릿의 빈 데이터를 채우고, 실제 로직빌더에서 열어볼 수 있는 flowData를 구성했다.
- 템플릿 삭제 버튼과 사용자 워크플로우 삭제 흐름을 보강했다.
- 편집 버튼을 누르면 로직빌더로 이동하고, 기존 템플릿 구조를 확인/수정할 수 있도록 했다.

### 4.6 스케줄러

- 일정 등록에서 단순 시간 선택뿐 아니라 기간 기반 입력을 반영했다.
- 여행 일정처럼 시작일과 종료일을 정할 수 있는 흐름으로 개선했다.
- 24시간 일정이나 여러 시간대 일정이 타임라인에 제대로 표시되도록 수정했다.
- 일정 상세/수정 모달의 데이터 구조와 화면 반영 흐름을 정리했다.

## 5. 시연용 MQTT 센서 시뮬레이터

기존에는 실제 센서 없이 Farm Flow가 센서 데이터를 받는 모습을 보여주기 어려웠다.

최종 코드에는 `tools/mqtt-sensor-simulator.html`을 추가하여 브라우저에서 직접 센서 값을 조정하고 MQTT로 전송할 수 있게 했다.

시뮬레이터에서 가능한 시연:

- 온실 UID 입력
- 온도 센서 값 조정
- 습도 센서 값 조정
- CO2 센서 값 조정
- 조도 센서 값 조정
- 환기팬, 스프링클러, 보광등 제어기 UID 입력
- MQTT WebSocket으로 브로커에 telemetry 발행
- Farm Flow 대시보드에서 값 변화 확인
- 로직 조건 만족 시 제어기 상태 변화 확인

이 기능 덕분에 실제 라즈베리파이나 아두이노가 없어도 노트북/브라우저만으로 MQTT 기반 센서 연동 시연이 가능해졌다.

## 6. 배포 및 운영 변경 사항

### 6.1 Cloudflare 도메인 배포

- `farmflow.iotbigdata.store` 도메인을 Cloudflare에 연결했다.
- Cloudflare Tunnel을 사용하여 외부 사용자가 로컬 PC에서 실행 중인 Farm Flow에 접속할 수 있게 했다.
- 프론트 정적 빌드와 백엔드 API를 하나의 public server에서 제공하도록 구성했다.

### 6.2 Public Server

- `tools/farmflow-cloudflare-server.js`를 추가했다.
- 역할:
  - `frontend/dist` 정적 파일 제공
  - `/api/*` 요청을 백엔드 `127.0.0.1:8080`으로 프록시
  - `/mqtt` WebSocket 요청을 MQTT 브로커 `9001`로 프록시
  - `/__health` health check 제공

### 6.3 자동 시작

- `tools/start-farmflow.ps1`을 추가했다.
- PC 부팅 후 자동으로 아래 서비스를 올릴 수 있게 했다.
  - Docker Desktop
  - PostgreSQL
  - Redis
  - InfluxDB
  - Mosquitto MQTT
  - Spring Boot 백엔드
  - Node public server
  - Cloudflare Tunnel
- 전기 차단 이후 부팅 직후 네트워크가 늦게 살아나는 문제를 고려하여 Cloudflare DNS/API 대기와 터널 3회 재시도 로직을 추가했다.

## 7. 발표에서 강조할 수 있는 핵심 포인트

### 7.1 기존 프로젝트에서 달라진 점

Farm Flow는 단순히 화면을 보여주는 웹 서비스에서, 사용자별 온실 UID를 기준으로 센서 데이터와 장치 제어를 분리하고 MQTT 기반 실시간 데이터 흐름까지 시연할 수 있는 구조로 확장되었다.

### 7.2 백엔드 강조 포인트

- JWT 기반 인증
- 사용자별 온실 UID 발급
- 장치 등록과 온실 데이터 분리
- MQTT telemetry 수신
- 룰 엔진 기반 자동 제어
- 워크플로우/템플릿 저장 및 배포 구조

### 7.3 프론트엔드 강조 포인트

- 센서 데이터가 실시간으로 바뀌는 대시보드
- 직접 구성 가능한 로직빌더
- 시연용 템플릿과 워크플로우 관리
- 기간 기반 스케줄러
- 알림센터와 제어 상태 표시

### 7.4 시연 강조 포인트

- 실제 센서가 없어도 MQTT 시뮬레이터로 센서 입력을 재현할 수 있다.
- 센서 값이 변하면 대시보드가 바뀐다.
- 설정한 조건을 만족하면 제어기가 켜진다.
- 조건이 해제되면 제어기가 꺼진다.
- 여러 사용자는 각자의 온실 UID로 데이터를 분리할 수 있다.
- 외부 노트북에서도 `farmflow.iotbigdata.store`로 접속해 시연할 수 있다.

## 8. 발표자료용 한 문장 요약

Farm Flow는 기존의 정적인 스마트팜 관리 화면을 사용자별 온실 UID, MQTT 센서 시뮬레이터, 실시간 대시보드, 로직 기반 자동 제어, 템플릿과 스케줄러, Cloudflare 외부 배포까지 연결된 시연 가능한 스마트팜 통합 관리 시스템으로 확장했다.
